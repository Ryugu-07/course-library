实验 07 · 扩展机制选择器

对应第 23–25 章。本实验训练你把功能需求映射到指令、Skill、MCP、Hook、Plugin、Automation 或 Subagent。

1. 实验问题

“我想扩展 Agent”还不够具体。新能力可能是长期规则、工作方法、外部动作、机械约束、团队分发、定时触发或上下文隔离。选错机制会造成常驻上下文膨胀、权限过宽或难以维护。

先选择“在工具前后强制运行检查”。预测为什么 Skill 不是首选。

2. 运行选择器

分数是教学启发，不是产品兼容性判断。真实实现可以组合：一个 Plugin 同时安装 Skill、MCP 和 Hook；Automation 触发一个使用这些能力的 Agent Thread。

3. 七种问题七种抓手

  • AGENTS.md：每次都要遵守的项目行为；
  • Skill：按需加载的复杂方法；
  • MCP：Agent 外部的数据或动作；
  • Hook：生命周期上的确定性强制逻辑；
  • Plugin：安装、版本和团队分发；
  • Automation：时间或外部事件触发；
  • Subagent：独立上下文、工具或角色。

作用域也重要：一次任务放 prompt，当前仓库放项目配置，个人通用能力放用户目录，团队能力需要可审查分发。

4. 组合练习

设计“每晚审查依赖安全更新”：

  1. Automation 每晚触发；
  2. Skill 定义审查流程；
  3. MCP 或包管理工具读取外部公告；
  4. Subagent 分析不同依赖；
  5. Hook 扫描输出是否包含秘密；
  6. Plugin 把整套配置交给团队。

任何一种机制单独包办都会别扭。功能架构通常是职责组合。

5. 安全检查

外部写入工具需要审批和认证；Hook 是真实脚本，需要信任；Plugin 安装会扩大能力面；Skill 的脚本也不能因为“只是教材”就自动执行。机制越可复用，供应链风险越值得审查。

6. 功能设计挑战

拿你自己的设想，写下触发、上下文、决策、工具、状态、验证、权限、失败和输出，再用本实验选择扩展机制。若一个功能同时得到两个高分，通常说明它确实由两个职责组成，而不是选择器失败。

完成标准是能回答“为什么放这里”，而不是记住术语定义。
