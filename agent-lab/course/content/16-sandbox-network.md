# 第 16 章 · 沙箱、文件与网络

> 本章目标：理解沙箱如何把权限意图落实为操作系统边界，并学会分别设计文件、进程和网络访问。

## 1. 沙箱防的不是“坏模型”

模型可能因为错误推理、提示词注入或参数拼接做出危险动作。沙箱不判断动机，只限制进程能访问的资源。这种机械边界比提示词里的“请勿访问”可靠，因为模型无法通过换一种措辞取消操作系统规则。

以 Codex 的本地命令执行为例（资料核查 2026-10-28），read-only、workspace-write、full access 描述不同文件/命令权限配置；workspace-write 的命令沙箱通常限制写入根并默认关闭命令网络。具体生效配置可能被会话或管理策略改变。这些名称与默认值不是所有 Agent 的共同标准，更不是对每一种工具出口的统一承诺。

## 2. 文件系统边界

沙箱需要定义可读根、可写根和受保护路径。.git、SSH 配置、云凭据、浏览器资料和用户主目录通常应特殊保护。即使 workspace 可写，版本控制元数据也不应被普通模型命令随意修改。

路径检查属于应用层，操作系统沙箱属于执行层。两者同时存在时，即使某个工具漏掉路径校验，进程仍难以越界。

## 3. 命令断网，为什么 MCP 仍可能访问外部服务

联网扩大了数据泄露、供应链和提示词注入风险。一个仓库里的恶意说明可能诱导 Agent 上传源代码；包管理器可能执行第三方安装脚本；访问网页会把不可信文本带回模型上下文。

需要联网时，优先使用域名允许列表而不是开放全部出口。规则要处理精确域名、子域名、重定向、DNS 解析到私有地址和本地端口。允许 example.com 不应自动允许任意看起来相似的域名。

[Codex 官方说明](https://learn.chatgpt.com/docs/agent-approvals-security#traffic-outside-the-command-network-proxy)明确：本地命令网络代理约束沙箱内的命令及子进程，其他工具有各自的连接和控制。

| 路径 | 应检查的控制 | 一个命令探针不能证明什么 |
|---|---|---|
| Shell、脚本、子进程 | 命令沙箱、网络代理、目录和域名规则 | 不能代表所有 MCP 服务的权限 |
| MCP、Apps、连接器 | 服务配置、账号授权、工具与工作区策略 | 账号已登录不等于允许执行所有动作 |
| 浏览器、Computer Use | 功能权限、站点/来源规则、上传下载约束 | `curl` 失败不代表浏览器也离线 |
| 云任务、模型与认证请求 | 各环境或客户端的服务连接策略 | 本地命令允许列表不自动约束它们 |

**反例：**Shell 不能联网，但启用的远程连接器能读取云文档，两者不矛盾。若目标是“源码不得外发”，应逐条追踪哪些工具可以取得源码、能把数据交给谁，再验证这些路径；不能用一次断网命令宣布验收完成。

## 4. Setup 与 Agent 阶段分离

云端执行常把环境准备和 Agent 工作分成两阶段。Setup 可以联网安装依赖并使用临时秘密；Agent 阶段应用单独的网络策略，并在不再需要时移除 setup 专用秘密；具体默认值依环境而定。这样既能准备环境，又减少任务运行时的攻击面。

本地也可以借鉴：由人类或可信脚本预装依赖，Agent 只运行锁定版本；不要每次遇到缺包就允许模型自由联网安装最新版本。

## 5. 本地服务与回环地址

前端测试需要 Agent 访问 localhost，这与访问公网不同。网络策略可以显式允许某个回环端口，同时继续拒绝其他私有网段。宽泛允许本地网络可能暴露数据库、容器守护进程和内部管理接口。

Unix socket 也属于高风险通道。能访问 Docker socket 的进程通常等于拥有宿主高权限，因此不能因为它不是“网络”就忽略。

## 6. 验证沙箱

不要只读配置文件，要实际运行探针：能否写 workspace，能否写父目录，能否连接允许域名，能否访问被拒绝路径。每种启用的工具出口都要有独立探针，并记录宿主版本、配置和预期；只能在受控测试资源上运行，不为测试去接触真实秘密或写入真实服务。测试结果应进入回归，因为系统升级和平台差异可能改变边界。

!!! warning "边界扩大原则"
    遇到权限拒绝时，先寻找更窄的替代方案：允许一个目录、一条命令或一个域名，而不是切换到 full access。权限应随任务最小化，而不是随挫折最大化。
